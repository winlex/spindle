## 3. Границы скоупа (обязательные)

**Входит:** перечисленное в F1–F15 и N1–N12.

**Не входит (добавляем только с явного согласия):** файлы/вложения, email-уведомления, реалтайм,
аналитика, подзадачи, soft delete, K8s, Kafka/gRPC, CQRS/ES, i18n, публичный rate limiter.

**Правило:** новая фича не добавляется, пока не закрыты критерии приёмки текущего урока.
Каждое расширение скоупа фиксируется в `04-progress.md` с обоснованием.

## 5. Зависимости: запрещено

- Веб-фреймворки (gin, echo, fiber, chi) — пока не доказанная нехватка `net/http`.
- ORM/генераторы «из коробки» как основа (GORM, Ent) — обсуждаются на L30 как альтернатива,
  выбор делается осознанно, с замером сложности; по умолчанию — SQL руками или `sqlc`.
- DI-контейнеры (dig, uber/fx, wire).
- Собственные реализации JWT, bcrypt, UUID, роутера, ORM-клиента.
- Фреймворки для логирования (zap, logrus) — только `log/slog`.
- `interface{}`/`any`-словарь вместо типизированных структур ради «гибкости».

## 5.1. Политика безопасности зависимостей

Код зависимости **выполняется на машине разработчика во время `go build`/`go test`**, с правами
текущего пользователя. Поэтому «просто добавить библиотеку» — это решение о доверии, а не о
удобстве. Проверено эмпирически на Go 1.27.1: файлы модуля в кэше выставляются `r--r--r--`,
каталоги `dr-xr-xr-x`, `go mod verify` отвечает `all modules verified`.

Меры, применяемые в проекте:

1. **Белый список** (раздел 4) — основная мера. Чем меньше зависимостей, тем меньше поверхность.
   L01 — ноль зависимостей; далее максимум пять.
2. Осознанность добавления: `go mod why -m <модуль>`, `go mod graph`, `go list -m -u all`.
3. `go mod verify` в CI.
4. Чтение исходников в кэше перед добавлением — модули небольшие, это реально.
5. Сборка в контейнере (L44) — настоящая изоляция файловой системы, а не «другое место кэша».
6. `GOTOOLCHAIN=local` в CI — иначе тулчейн сам скачивает и запускает компилятор нужной версии.
7. `-mod=readonly` (дефолт) — сборка не может молча изменить `go.mod`.
8. `GOSUMDB` не отключается. `GOINSECURE` проверку sumdb **не** отменяет (проверено на 1.27.1);
   для приватных репозиториев применяются `GOPRIVATE`/`GONOSUMDB` осознанно и точечно.

## 6. Архитектурные рамки

Предпочтительная раскладка (обсуждается по мере роста, не навязывается заранее):

```
cmd/api/           main: конфиг, логи, сборка зависимостей, запуск, shutdown
internal/config/   чтение и валидация конфигурации
internal/platform/ инфраструктура: postgres, logger, metrics, jobs (очередь+воркеры)
internal/<feature>/ auth, projects, tasks, notifications — по функциональности
                    (domain, usecase/ service, http) внутри каждой фичи
```

Правила:
- Пакет верхнего уровня не содержит «логики всего подряд»; имя пакета отражает предметную область.
- Интерфейс объявляется в потребителе (usecase) и минимален по методам.
- Транзакция определяется границей usecase, а не репозитория.
- Зависимости передаются явно через конструкторы; `cmd/` — единственное место сборки графа.
- Нет пакетов `common`, `utils`, `helpers`, `base`, `models` без доменного смысла.

## 7. Definition of Done для проекта

- [ ] `docker compose up` поднимает сервис и БД, `/readyz` → 200.
- [ ] Все эндпоинты v1 реализованы, ошибки в едином формате.
- [ ] `go test -race ./...` зелёный, покрытие домена ≥ 80%.
- [ ] Graceful shutdown подтверждён: SIGTERM → нет ошибок, in-flight завершены.
- [ ] `/metrics` содержит HTTP-метрики и метрики очереди.
- [ ] CI зелёный, Dockerfile multi-stage, образ не от root.
- [ ] README: быстрый старт, архитектура, ключевые решения и их компромиссы, раздел «что НЕ сделано и почему».
- [ ] Нет `TODO`/`FIXME` в коде без ссылки на задачу; нет мёртвого кода.
- [ ] Есть 1–2 ADR-коротких раздела в README: транзакции, очередь на Postgres, отсутствие ORM.
