## Замечания

### Критические

**1. `gofmt -l .` не пусто — `make check` падает**

*Где:* `cmd/api/main_test.go`, последняя строка.

*Проверено:*
```
$ gofmt -l .
cmd/api/main_test.go
$ make check
cmd/api/main_test.go
код не отформатирован
make: *** [Makefile:34: fmt-check] Error 1
```

*Дифф:* файл сохранён без завершающего перевода строки.
```
-func TestRun(t *testing.T) { _ = run() }
\ No newline at end of file
+func TestRun(t *testing.T) { _ = run() }
```

*Почему это критично, а не мелочь.* В ответе в разделе 2.3 стоит «(пустой)». Скорее всего,
проверка выполнялась до того, как появился `main_test.go` — он приехал позже, с заданием О3.
Значит, чек-лист приёмки проходился в момент, когда он уже не мог быть пройден. Это и есть
главный риск любого чек-листа: **он проверяет состояние на момент прохождения, а не на момент сдачи.**
Перед сдачей нужно прогнать всё заново, целиком, одним заходом.

Формально сломан критерий Н1, и твоя же `fmt-check` в Makefile это ловит — то есть инструмент
работает, просто не был запущен на финальном состоянии.

*Как исправить:* `gofmt -w .`, затем `make check` — должен стать зелёным.

**2. `README.md` отсутствует**

*Где:* его нет в репозитории вообще.

*Почему это критично:* это Этап 5 задания и критерий приёмки №9. В портфолио README открывают
первым: у рекрутера нет времени читать код, чтобы понять, что это и как запустить.

*Как исправить концептуально:* три коротких раздела — что это, как запустить, что внутри.
Расширять будем на L48, но база нужна с первого коммита, чтобы в истории репозитория была
видна эволюция.

**3. `make build` собирает только `cmd/api`**

*Где:* `Makefile`, строка `CMD := ./cmd/api`.

*Проверено:*
```
$ make clean && make build && ls -1 bin/
api
```

*Почему это важно.* `bin/migrate` и `bin/spindle-api`, которые ты запускал, остались от
прошлых сборок. На чистой машине `make build && ./bin/migrate` не сработает — файла не будет.
Ты сам объяснил в О5, что миграции собираются отдельно, и здесь же сделал наоборот.

*Как исправить концептуально:* покрыть все команды одной строкой — `go build -o $(BIN)/ ./cmd/...`.
Не надо перечислять каталоги: их число будет расти, а правило останется работать.

### Важные

**4. Импорты не разбиты на группы**

*Где:* `cmd/api/main.go` и `internal/buildinfo/buildinfo_test.go`.

```go
import (
	"fmt"
	"github.com/winlex/spindle/internal/buildinfo"
	"os"
)
```

*Почему это важно.* `gofmt` сортирует импорты лексикографически и понятия группы не имеет:
`fmt` < `github.com/...` < `os`, всё «правильно», и `gofmt -l` молчит. Но по соглашению Go
импорты делят на группы: сначала стандартная библиотека, пустая строка, затем сторонние и
локальные. Сейчас чужой пакет стоит между `fmt` и `os`.

Отдельно: `gofmt` этого не проверяет, проверяет `goimports`. На этом уроке подключать его
не нужно, но на L23, когда дойдём до `slices` и `maps`, обсудим.

*Как исправить концептуально:* одна пустая строка между группами. `gofmt -w` её сохранит.

**5. Разделы 2.1, 2.2, 3, 4 ответа не заполнены**

*Где:* `answers/L01.md` — структура проекта, код, вывод дерева, ключевые решения.

*Почему это важно.* Ревью строится на артефакте, а не на догадке: воспроизводимый отчёт важнее
того, что «примерно понятно». Раздел 3 («Ключевые решения и почему») — самый ценный: там видно,
где ты думал сам, а где переписал. Раздел 4 заполнен частично: «Что гуглил» — это список вопросов
из чата, а «Где застрял и что нашёл» — пусто, хотя застрял ты как минимум трижды.

*Как исправить концептуально:* код в ответ можно не дублировать, достаточно ссылки на коммит и
имён файлов. Но рассуждения — обязательно, их нигде больше нет.

**6. Ответ на В3 — про линтер, а не про `go vet`**

*Где:* `answers/L01.md`, В3.

> Проверяет общепринятые сообществом стилистику кода, но не его работоспособность

*Почему это важно.* `go vet` не проверяет стиль. Он проверяет подмножество настоящих ошибок:
неправильные аргументы в `printf`-подобных вызовах, копирование объектов с блокировкой
(`sync.Mutex`), недостижимый код, ошибочные `fmt.Sscan`-вызовы. Стиль — это уже линтер, и
подключим его на L47. Это единственный ответ, где фактическое содержание не соответствует вопросу.

*Как понять правильно:* `go vet` отвечает на вопрос «сломается ли это или сработает не так,
как я думаю», а не «красиво ли написано».
