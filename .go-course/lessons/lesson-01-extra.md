## A. Что создаёт `go build`, а что — нет → к О5

**Правило: `go build` создаёт файл, только если в аргументах ровно один main-пакет.**
Во всех остальных случаях компилирует и выбрасывает результат — остаётся проверка компиляции.

| Команда | Что делает | Файлы в каталоге |
|---|---|---|
| `go build ./...` | проверить компиляцию всего | **ни одного** |
| `go build ./cmd/...` | то же, только main-пакеты | **ни одного** |
| `go build .` | текущий каталог как пакет | ошибка `no Go files in …`, если в корне нет `.go` |
| `go build ./cmd/api` | один main-пакет | `api` в текущем каталоге |
| `go build -o bin/ ./cmd/...` | все main-пакеты в каталог | `bin/api` + `bin/migrate` |
| `go build -o bin/spindle-api ./cmd/api` | один пакет, имя задано явно | `bin/spindle-api` |

**Точка и три точки — не одно и то же.** `.` — текущий каталог как единственный пакет.
`./...` — «все подкаталоги, где есть Go-файлы». В корне нашего модуля только `go.mod`,
`README.md` и `.gitignore`, поэтому `go build .` честно отвечает `no Go files in …`.
Указывай пакет явно: `./cmd/api`, `./cmd/migrate`, `./cmd/...`.

Когда пакет один, `go build` догадывается сам и называет результат именем пакета. Когда пакетов
много — догадываться не о чем, и Go ничего не пишет, чтобы не устроить свалку. **Код возврата
в обоих случаях 0**, поэтому «собралось» и «собралось с артефактом» — разные утверждения.

Так Go разделяет две задачи, которые их путают:

- **«проверить, что всё компилируется»** — dev и CI. Компилировать 200 пакетов ради факта
  успеха нормально, артефакт не нужен. Это `go build ./...`;
- **«собрать бинарники для деплоя»** — релиз. Нужен конкретный файл, поэтому `-o` явный.
  Несколько main-пакетов → `-o` указывает на **каталог** с завершающим слэшем, Go раскладывает
  результаты по именам пакетов. Если дать файл — ошибка, несколько пакетов в один не сойдутся.

**Почему `migrate` — отдельный бинарник, а не флаг у `api`.** У бинарника может быть свой
жизненный цикл: `api` живёт месяцами и скопирован на 50 серверов, `migrate` запускают раз в
неделю с флагами (вперёд, назад, до версии). Флаг у `api` заставил бы утилиту инициализировать
весь HTTP-сервер, конфиг и соединение с БД — и раздул бы бинарник втрое ради функции, которая
нужна раз в неделю.

## B. `package X` против `package X_test` → к разделу 3.4 урока

В одном каталоге разрешены **два** пакета: `X` и `X_test`. Разница не в оформлении, а в том,
что они видят друг от друга.

**`package X_test` — отдельный пакет.** Он видит из `X` **только экспортируемые** идентификаторы:
`New`, `Info`, `StartedAt` — да; `run`, `version` — нет, для внешнего пакета их не существует.

| Что тестируешь | Какой пакет указывать |
|---|---|
| Только то, что видит потребитель снаружи | `package X_test` |
| Нужно дотянуться до неэкспортируемого | `package X` |
| Сомневаешься | начать с `package X`, потом переключить |

**Почему внешний пакет лучше по умолчанию.** Он проверяет API так, как его увидит потребитель,
и не даёт случайно протестировать внутренние детали. Если тест проходит, но дергает
неэкспортируемое поле — он привязан к реализации, а не к контракту, и сломается при любом
легитимном рефакторинге.

**Проверяемая ошибка.** Попытка протестировать `run` из внешнего пакета:

```go
package main_test

import "testing"

func TestRun(t *testing.T) { _ = run() }
```

```
cmd/api/main_test.go:5:34: undefined: run
```

Пара `main` + `main_test` формально разрешена, и компилятор не жалуется на имена. Но `run`
начинается с маленькой буквы, значит не экспортируется, и для внешнего пакета его **не
существует**. Рабочий вариант — `package main`.

**Типичная ошибка новичка: импорт собственного пакета.** Файлы одного каталога видят друг друга
напрямую, импорт не нужен. Если написать его всё равно:

```go
package main_test

import (
	"main"          // ← Go ищет пакет main в стандартной библиотеке
)
```

```
cmd/api/main_test.go:4:3: package main is not in std (/usr/local/go/src/main)
```

`main` — зарезервированное имя точки входа, импортировать нельзя. Сообщение `not in std`
**всегда** означает одно: ты импортируешь путь, которого нет в стандартной библиотеке, и Go
пошёл искать его en `GOROOT/src/`. Начало сообщения содержит файл, строку и столбец — позицию
проблемного токена. Здесь `4:3` — кавычка перед `main`.

**Общее правило чтения ошибок.** Компилятор останавливается на **первой** ошибке. В файле
из 7 строк их было три, и показывалась одна: ошибка про импорт маскировала неверное имя пакета
и забытый `testing`. Чини по одной, перезапускай.

## C. Почему `main` показывает 0% в покрытии → к О3

**Сначала, что такое точка входа в Go.** Не файл, а **пакет**: директория с `package main`
и обязательной `func main()`. Её вызывает рантайм при старте бинарника. Точка входа
определяется тем, какой каталог помечен как `main` при сборке.

Три причины нуля в отчёте, наложенные друг на друга:

1. **Её зовёт рантайм, а не тест.** Формально покрыть можно — достаточно
   `func TestMainFunc(t *testing.T) { main() }`, и `main.go:9` станет 100%. Но смысла ноль:
   тест проверяет не логику, а факт исполнения строки.

2. **Она в отдельном пакете, и пакеты не делят покрытие.** `cmd/api` и `internal/buildinfo` —
   два независимых пакета. 100% у второго никак не влияет на первый. Общий процент — среднее
   по операторам всех пакетов, и нули тянут его вниз.

3. **Главная: `os.Exit` убивает тестовый процесс.** Дошёл до `os.Exit(1)` или `panic` — процесс
   завершается, `defer` не выполняется, профиль не пишется, а **все тесты пакета, идущие после,
   не запускаются**. Проверяется так: положи в `main.go` `os.Exit(1)`, напиши три теста, из
   которых последний зовёт `main()` — отработает только первый.

**Что делают на практике:**

- гнаться за покрытием `main` бессмысленно, его не покрывает никто;
- полезная цель — покрыть **`run()`**: добавь `func TestRun(t *testing.T) { _ = run() }`,
  `run` станет 100%, общий процент вырастет, а `main` останется нулём. **Запрет на логику
  в `main` существует именно ради этого**;
- пакеты из `cmd/` исключают из целевого покрытия, порог считают по `./internal/...`;
- «28%» для проекта без `internal/` не значит ничего.

**Сравнение с PHP/TS.** В PHP вход — `public/index.php`, в Node — `server.js`, и туда привычно
писать полстраницы: настроить БД, создать контейнер, инициализировать фреймворк. В Go точка
входа — **пакет, а не место для кода**. Разница не в традиции, а в следствии: нет ни контейнера,
ни автозагрузки, ни неявных зависимостей, которые нужно «настроить перед стартом». Всё передаётся
явно конструкторами — и делается это в `main`.

## D. Метаданные сборки → к О6

### `fmt.Stringer` — контракт, а не пакет

Ровно одна строчка в `fmt/print.go`:

```go
type Stringer interface {
	String() string
}
```

Объявил метод — и `fmt` применяет его сам:

```
%v    → spindle-api v0.1.0 (go go1.27.1)
%s    → spindle-api v0.1.0 (go go1.27.1)
%q    → "spindle-api v0.1.0 (go go1.27.1)"
%T    → main.Info        ← тип остался Info
```

**Важное: `%T` по-прежнему показывает `main.Info`.** Реализация `Stringer` **не меняет тип
значения**, влияет только на вывод. Наш `String()` — не самодельная фишка, а вход в стандартный
механизм.

Проверка на этапе компиляции — пустое имя `_` означает «значение не используй, нужно проверить»:

```go
var _ fmt.Stringer = buildinfo.Info{}
```

### `runtime/debug.BuildInfo` — аналог, и он полнее

`runtime/debug/mod.go:41` и `:108`:

```go
type BuildInfo struct {
	GoVersion string          // "go1.27.1"
	Path      string          // путь главного пакета
	Main      Module          // модуль, содержащий main
	Deps      []*Module       // все зависимости
	Settings  []BuildSetting  // параметры сборки
}

func (bi *BuildInfo) String() string   // тот же приём, что у нас
```

Вывод бинарника, собранного из git-репозитория с тегом:

```
go	go1.27.1
path	spindle/cmd/version
mod	spindle	v0.1.0
build	-buildmode=exe
build	-compiler=gc
build	CGO_ENABLED=0
build	GOARCH=arm64
build	GOOS=linux
build	vcs=git
build	vcs.revision=00c380db6792e325470583841ce9c85d1629b476
build	vcs.time=2026-09-30T14:51:31Z
build	vcs.modified=false
```

| | Наш `Info` | `debug.BuildInfo` |
|---|---|---|
| Источник | `runtime.Version()` + наша `var version` + `time.Now()` | вкомпилировано бинарником при сборке |
| Ревизия git | нет | `vcs.revision` |
| Время коммита | нет | `vcs.time` |
| Дерево было грязным | нет | `vcs.modified` |
| Флаги сборки | нет | `-compiler`, `CGO_ENABLED`, `GOOS`, `GOARCH` |
| Зависимости | нет | весь `Deps` |

**`runtime.Version()`** — просто доступ к строке версии, без форматирования. Это же значение
лежит в `BuildInfo.GoVersion`.

**`go version -m ./binary`** отдаёт то же самое, но **для готового файла, без запуска**. В
расследованиях это то, чем пользуются: «кто собрал этот файл, из какого коммита и с какими
флагами». Поэтому `vcs.revision` ценен — по строке в логе при старте находишь нужный коммит.

### Два блока получены принципиально разными способами

```bash
git add -A && git commit -m "add version tool" && git tag v0.1.0
mkdir -p bin && go build -o bin/ ./cmd/... && ./bin/version
```

- `build -ldflags=...` — компилятор **записал**, какие флаги линковки ты дал. Саму строку
  он не подставлял;
- `build vcs.*` — компилятор **подставил сам**, без `-ldflags`, потому что умеет ходить в git.

### Прочитал и внедрил — разные операции

Здесь легко сделать неверный вывод, поэтому явно.

| Операция | Механизм | Кто реализует |
|---|---|---|
| **Прочитать** метаданные сборки | `debug.ReadBuildInfo()` | stdlib, для своих полей |
| **Внедрить** значение в свою переменную | `-ldflags -X` | ты: руками или своим кодом |

`Main.Version` — **поле чужой структуры внутри stdlib**. Это не «версия нашего пакета» и не
замена нашей переменной. `ReadBuildInfo()` читает то, что компилятор записал, а записать он может
лишь то, до чего дотянулся: git, флаги, путь модуля. Механизма «внедрить тег в **твою**
переменную» не существует — компилятор не знает, что твоя `version` про версию.

**Проверяемое следствие: тег git на нашу `var version` не влияет никак.**

| Состояние git | наша `var version` | `Main.Version` |
|---|---|---|
| тега нет | `dev` | `v0.0.0-20260930152454-118e7cb14d74` |
| тег на HEAD, дерево грязное | `dev` | `v0.1.0+dirty` |
| тег на HEAD, дерево чистое | `dev` | **`v0.2.0`** |
| значение передано через `-X` | **`v0.2.0`** | `v0.2.0` |

Правило формирования `Main.Version`: чистый тег **только** когда HEAD стоит ровно на теге и
дерево чистое. На следующем коммите Go уже не может сказать «это релиз v0.1.0» и откатывается
к псевдоверсии.

### Границы `-X`

`-X` — единственный канал внедрения, и условия жёсткие. Проверено:

| Случай | Результат |
|---|---|
| `var ok = "dev"` — пакетная строка | `ok = v1.0.0` ✅ |
| `var num = 42` — не строка | ошибка `cannot set with -X: not a var of type string` |
| `var computed = fmt.Sprint(1)` — инициализирована вызовом | осталось `1`, **подмена не сработала, ошибки нет** |
| `local := "dev"` — локальная | осталось `dev`, `-X` её не видит |

**Только пакетные, только строковые, только инициализированные константной строкой.** Третье
правило коварное: переменная объявлена, подмена молча не срабатывает, код возврата 0. Именно
поэтому `var version = "dev"` в нашем пакете объявлен правильно — под все три требования.
На L48, добавляя `buildTime`, помни: `var buildTime = time.Now()` подставиться не даст.

### Сборка без git: почему своя переменная незаменима

В Docker-образе каталога `.git` нет, и компилятор не может узнать ревизию. Ключ
`-buildvcs=false` имитирует это:

```
=== обычная сборка из git ===
Main.Version : v0.2.0+dirty
vcs.revision : 429d891f65f76dc12eb444e3c95030f4f030b54e
vcs.time     : 2026-09-30T15:25:05Z
vcs.modified : true

=== -buildvcs=false (как в Docker) ===
Main.Version : (devel)        ← сдулось
vcs.*        : ОТСУТСТВУЕТ    ← пропало всё
```

Поэтому «нужна ли своя переменная» решается не в общем виде, а по сценарию:

- **собираешь из git, семантическая версия устраивает** — своя не нужна, хватит `Main.Version`;
- **нужен формат, который Go не производит** (`2026.09.30-rc1`, `build-2291`) — своя нужна;
- **сборка без git (Docker, артефакт из CI, чужая машина)** — своя обязательна.

### Что взять в проект на L48

```json
{
  "service":    "spindle",
  "version":    "v0.2.0",              // наш тег из -X
  "commit":     "00c380db...",         // vcs.revision
  "built_at":   "2026-09-30T14:51Z",  // vcs.time — момент коммита
  "started_at": "2026-09-30T15:20Z",  // запуск процесса
  "go":         "go1.27.1",
  "dirty":      false                  // vcs.modified
}
```

`built_at` и `started_at` — разные вещи. Наш `StartedAt: time.Now()` — время запуска процесса;
для логов при старте («сколько работает») это верно. Но на вопрос «какой код работает» отвечает
`vcs.time`. Поэтому `time.Now()` в `StartedAt` для ручки `/version` — плохая идея: прожив полгода,
ручка покажет дату полугода назад, и это прочтётся как «версия изменилась полгода назад».

### `cmd/version` — готовый инструмент

Третий бинарник, который ничего не делает, кроме показа и сравнения:

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/debug"
	"time"

	"github.com/твой-логин/spindle/internal/buildinfo"
)

var _ fmt.Stringer = buildinfo.Info{}

func main() {
	ours := buildinfo.New()
	fmt.Printf("наш пакет : %s\n", ours)          // %v сам вызовет String()
	fmt.Printf("время Go  : %s\n", runtime.Version())

	bi, ok := debug.ReadBuildInfo()
	if !ok {
		fmt.Fprintln(os.Stderr, "build info недоступно")
		os.Exit(1)
	}
	fmt.Print(bi)                                  // вызовет (*BuildInfo).String()

	for _, s := range bi.Settings {
		switch s.Key {
		case "vcs.revision", "vcs.time", "vcs.modified":
			fmt.Printf("%-13s: %s\n", s.Key, s.Value)
		}
	}
	fmt.Println("started_at :", ours.StartedAt.Format(time.RFC3339))
}
```

Три способа вызвать `String()` дают одинаковый результат: `fmt.Println(ours)`, `fmt.Printf("%s", ours)`,
`ours.String()`. `fmt.Print(bi)` работает так же — у `BuildInfo` свой `String()`.

## E. Языковая версия, generic-методы, CI → к О4

**Языковая версия ≠ версия компилятора.** Строка `go 1.26.0` в `go.mod` — не инструкция
компилятору, а декларация: «модуль не использует языковых возможностей новее 1.26». Компилятор
остаётся `go1.27.1`.

**Что такое generic-метод.** Обычный обобщённый тип задаёт параметры типа при объявлении.
Generic-метод объявляет **собственные, дополнительные** — фича Go 1.27:

```go
// Параметры типа метода: K, V — от типа Cache, W — собственный параметр метода
func (c *Cache[K, V]) MapValues[W any](fn func(V) W) *Cache[K, W] {
	out := &Cache[K, W]{m: make(map[K]W, len(c.m))}
	for k, v := range c.m {
		out.m[k] = fn(v)
	}
	return out
}
```

До 1.27 так написать было нельзя — пришлось бы делать функцию уровня пакета:

```go
func MapValues[K comparable, V, W any](c *Cache[K, V], fn func(V) W) *Cache[K, W]
```

Разница в читаемости: `cache.MapValues(fn)` против `MapValues(cache, fn)`. Ограничение:
**методы интерфейсов не могут иметь параметры типа**, и generic-метод интерфейс не реализует.

**Реакция компилятора при понижении версии:**

```
$ go mod edit -go=1.26.0 && go build ./...
./cache.go:11:33: generic method requires go1.27 or later (-lang was set to go1.26; check go.mod)
```

Читай сообщение: `-lang was set to go1.26; check go.mod` — компилятор прямо указывает причину.
Это **не ошибка кода**: код корректен, он написан на языке, который модуль объявил недоступным.

**Проверка ленивая, срабатывает на фиче, а не на версии.** Пока ты не **написал** что-то новое,
понижение не даёт видимых эффектов: один и тот же тулчейн собрал generic-метод при `go 1.27.1`
и отказался при `go 1.26.0`.

**Про `stdversion`.** Анализатор `go vet` «report uses of too-new standard library symbols»
существует и документирован, но воспроизвести его срабатывание на практике не удалось:
`go vet -stdversion` промолчал и на `strings.CutPrefix` при `go 1.16.0`, и на `errors.Is` при
`go 1.12.0`. Единственный надёжный барьер — компилятор. Полагаться на `stdversion` как на
основную защиту не стоит.

**Что изменится для CI.** Сценарий: в `go.mod` стоит `go 1.27.0`, в образе — Go 1.26.

| `GOTOOLCHAIN` | Поведение |
|---|---|
| `auto` (по умолчанию) | Go **сам скачает** тулчейн 1.27. Работает, но требует сети и места на диске |
| `local` | Сборка **упадёт**: `go.mod requires go >= 1.27.0 (running go 1.26.x)` |

Практические следствия:

1. **Локальная сборка и CI могут использовать разные компиляторы.** Фича, прошедшая дома на 1.27.1,
   упадёт в CI на 1.26. Правильный CI фиксирует версию **точно**, а не «последнюю».
2. **Автоскачивание в CI — скрытая зависимость.** Тянет из сети, падает без доступа, медленный.
3. **Понижение языковой версии — осознанный ход.** `go 1.26.0` означает «обязан собираться у всех,
   у кого есть 1.26». Плюс — шире совместимость, минус — недоступны новые фичи. Для приложения
   в портфолио не нужно; для библиотеки — иногда обязательно.
4. **`go 1.27.0` против `1.27.1`.** Второе жёстче: требует патч. Для приложения без разницы,
   для библиотеки лучше указывать минорную.

**Рекомендация для Spindle:** вернуть `go 1.27.1`. Мы не библиотека, совместимость со старым Go
не нужна, и через полгода упрёмся в собственное ограничение.

## F. Почему в Go не бывает `utils` → к В7

Урок говорит правило («никаких `utils`, `helpers`, `common`, `base`»), но не даёт обоснования.
Здесь оно — четырьмя механизмами, каждый проверяется компилятором.

#### 1. Циклы импортов — главная причина

```
internal/common/text.go
    func TaskSummary(t tasks.Task) string     // захотел знать про Task
```

`common` теперь зависит от `tasks`. И `tasks` **не может** использовать ничего из `common`:
компилятор вернёт `import cycle not allowed`. А ему почти наверняка понадобится — подпись для
логов, форматирование, проверка статуса задачи.

В PHP такое проходит: autoloader разрешает обе ссылки, в худшем случае рекурсия на вызове. Там
зависимость между классами — соглашение, которое компилятор не проверяет. В Go запрет циклов —
свойство языка, и вопрос «где живёт общий код» становится не вопросом вкуса, а вопросом с
ответами «здесь» или «никак».

#### 2. Методы объявляются только на локальных типах

```go
// utils
func FormatTask(t Task) string { ... }
```

Вызов обязан быть квалифицированным: `utils.FormatTask(t)`. Метод `t.DisplayName()` здесь
не написать никогда — компилятор не даст объявить метод для типа из чужого пакета. Значит,
любая «удобная» функция над доменным типом остаётся шумным вызовом и **неизбежно затаскивает
`utils` в зависимости домена** — а это путь к пункту 1.

#### 3. Пакет — это контракт, а у мешка контракта нет

30 экспортированных функций невозможно описать одним предложением. На вопрос «нужен ли мне этот
пакет?» ответа нет — только перебор тридцати имён. Пакет существует, чтобы его можно было
заменить целиком и описать одной строкой в документации. Мешок этого не даёт: он не заменяемый,
потому что ни одна его часть не имеет смысла вне остальных двадцати девяти.

#### 4. Радиус взрыва при переименовании

`utils.EmailValid` → `auth.ValidateEmail`: правка в каждом файле, где вызывалось. Если функция
живёт в `auth`, меняется только там, а у вызывающих — одна строка импорта, и то не всегда.

#### Куда кладать на самом деле

| Ситуация | Решение |
|---|---|
| Помощнику нужны доменные типы | В доменный пакет. Экспортируется, если нужен снаружи |
| Помощник типовой и домена не знает | Сначала в stdlib: `slices`, `maps`, `strings`, `errors`, `cmp`. Нет — возможно, не нужен |
| Двум пакетам нужно одно и то же | Дублировать. Пять строк лучше неправильной зависимости |
| Непонятно, куда | Тест: «удали пакет — что сломается?» Если «всё, но неясно где» — это мешок |

#### Проверка на stdlib

Пакетов `util`, `helper`, `common` в стандартной библиотеке нет. Совпадения по подстроке —
`httputil`, `imageutil`, `randutil`, `ioutil` — все названы **по предмету**, а не по роли.
Стандартная библиотека организована по доменам: `net`, `http`, `time`, `errors`, `slices`.

#### Почему это не модульность

У мешка **внешняя** сторона модульности: код разделён по папкам, и это создаёт видимость
разделения. **Внутренней** нет — у пакета нет предмета, который можно назвать, нет границ,
которые можно очертить, и нет смысла, по которому его можно заменить целиком. Видимость без
содержания.

#### Связь с PHP

В Symfony `App\Utils\DateHelper` со статическими методами — обычное дело, и никто не морщится:
импорт разрешается по имени, класс видит любой другой класс, «слой утилит» стоит над доменом без
последствий. В Go та же структура ломает сборку. Правило «не делайте `utils`» — не эстетическое
требование сообщества, а следствие запрета циклов и правила о методах.

## G. `internal/` — механизм, а не соглашение → к В2

Урок, раздел 3.4: «директория `internal/` — код из неё виден только внутри дерева, содержащего
`internal`. Это механизм запрета, а не соглашение». Разбор границ:

```
spindle/
├── internal/          ← только здесь
│   ├── buildinfo/
│   └── tasks/
└── cmd/api/main.go    ← тоже здесь: cmd/ внутри дерева модуля
```

Любой пакет, чей путь содержит `internal`, доступен **только** пакетам того же дерева, где
`internal` — общий корень. Попытка импортировать снаружи:

```
use of internal package github.com/winlex/spindle/internal/buildinfo not allowed
```

Ошибка **на этапе сборки**, а не в рантайме и не на ревью. Это и есть разница с соглашением
«не импортируйте utils»: договорённость нарушают молча и узнают на проде, `internal` нарушить
нельзя.

**Что это даёт на практике.** Внутренности модуля нельзя случайно сделать публичным API и нельзя
завязать на них чужой код. Случайно ушедшая наружу зависимость превратилась бы в публичный
контракт, который придётся поддерживать вечно. `internal` — это заявка: «здесь может меняться
что угодно, внешних потребителей нет».

**Про `cmd/`.** Он не даёт такой защиты — импортировать `cmd/api` извне можно. Поэтому в `cmd/`
складывают только точки входа, а всё с логикой — в `internal/`. Иначе любой может импортировать
твой `main` как библиотеку.
