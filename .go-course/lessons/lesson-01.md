# L01 — Toolchain, модуль и каркас Go-проекта

Модуль 0 · Ориентир 45–60 минут · Версия Go: актуальная стайбл **1.27.x**

---

## 1. Название и цель

**Название:** Go с нуля: toolchain, модуль, структура проекта, первые команды.

**Цель:** поставить Go, создать репозиторий проекта Spindle, собрать первый бинарник,
разобраться в том, как устроены модуль, пакет и «точка входа», и закрепить набор команд,
которыми ты будешь пользоваться каждый урок: сборка, запуск, форматирование, vet, тесты.

## 2. Что я должен уметь после урока

- Объяснить разницу между «модулем», «пакетом» и «командой» (`package main`).
- Создать модуль с правильным module path и объяснить, что такое директива `go`.
- Знать, где лежат зависимости, и почему в `go.mod` сейчас будет ровно одна строка `module`.
- Правильно использовать: `go build`, `go run`, `go test`, `gofmt`, `go vet`, `go doc`, `go list`.
- Понимать, почему проект начинается с `cmd/` + `internal/`, а не с `bin/`, `src/`, `app/`.
- Написать пакет с экспортируемым API, тест и `main`, который только связывает зависимости.

## 3. Краткая теория

### 3.1. Компиляция и артефакт

Go компилируется в **один статический бинарник**. В нём нет ни интерпретатора, ни PHP-FPM,
ни `node_modules`, ни виртуальной машины. На старте курса — версия **1.27.x** (актуальная стайбл;
проверь `go version`, фактическую версию патча сообщи).

Кросс-компиляция задаётся переменными окружения: `GOOS`, `GOARCH`. Тулчейн Go состоит из:

- команды `go` (драйвер: `mod`, `build`, `test`, `run`, `vet`, `fmt`, `doc`, `list`, `tool`, `env`);
- компилятора и линкера;
- стандартной библиотеки.

Побочный эффект, полезный для понимания: скорость сборки позволяет использовать «build-time
проверки» вместо рантайм-фреймворков. Именно поэтому проверки типов, `go vet`, линтеры и тесты
в Go дешёвые — их можно гонять постоянно.

### 3.2. Модуль

Модуль — это папка с `go.mod`:

```
module github.com/твой-логин/spindle   // module path: одновременно корень импортов
go 1.26.0                                // языковая версия
```

**Важная деталь про версии — прочитай, здесь легко ошибиться (и я сам ошибся, а потом проверил).**

В `go.mod` есть директива `go`, и её легко спутать с версией компилятора. Это **разные вещи**:

- `go 1.27.1` в `go.mod` — *языковая версия модуля*: какая версия спецификации языка применяется
  к этому модулю. Она ограничивает, какими языковыми возможностями можно пользоваться, и её учитывают
  линтеры, `go fix` и проверка `stdversion` в `go vet`;
- `go env GOVERSION` → `go1.27.1` — версия **компилятора**, которым ты сейчас собираешь.

История, из-за которой путаница частая: начиная с Go 1.26 команда `go mod init` в новых модулях
по умолчанию записывает языковую версию **ниже** текущей, чтобы модуль собирался у всех, у кого
есть поддерживаемая версия Go. Но поведение зависит от того, какой именно тулчейн у тебя стоит,
и правило менялось между релизами. **Поэтому не заучивай — проверь:**

```bash
go version                 # версия тулчейна
go mod init example.com/t && cat go.mod   # какую языковую версию он записал
```

На момент написания урока: тулчейн `go1.27.1` записывает `go 1.27.1`. Если у тебя после установки
получилось другое значение (например, `go 1.26.0`) — это не ошибка, а то самое правило. Напиши мне
фактические значения, и я объясню, что именно применилось.

Изменить явно: `go mod edit -go=1.27.0`. Оставим значение, которое создаст тулчейн, и обсудим
последствия, когда дойдём до generics и `encoding/json/v2`.

Ещё один механизм: `GOTOOLCHAIN`. С Go 1.21 тулчейн умеет сам скачать компилятор нужной версии,
если её требует `go.mod` или если ты явно попросил (`go1.27.1`). Значения: `auto` (по умолчанию),
`local` (использовать только установленный).

### 3.3. Зависимости

Зависимости объявляются в `go.mod` (`require`), их версии выбираются по правилу минимальной версии
(MVS), контрольные суммы — в `go.sum`. Локально всё скачивается в кэш модулей (`go env GOMODCACHE`),
`vendor/` в Go не обязателен.

`go get` — «добавить зависимость» (с изменением `go.mod`), `go mod tidy` — «привести `go.mod` и
`go.sum` в соответствие реальным импортам». В быту ты будешь пользоваться преимущественно
`go mod tidy` и `go get pkg@version`.

### 3.4. Пакет = директория

Правила, которые нужно запомнить:

- одна директория — один пакет; имя пакета совпадает с именем директории (регистр игнорируется);
- имя файла **никак** не связано с типом, который в нём объявлен: можно держать `Task`,
  `Transition` и `errors.go` в одном `domain/tasks.go` — это нормально;
- экспорт определяется регистром первой буквы: `New`, `Info`, `StartedAt` — наружу, `new`, `info` — нет;
- пакета с именем `main` быть должно ровно столько, сколько у тебя бинарников; в нём обязательна
  `func main()`;
- директория `internal/` — код из неё виден только внутри дерева, содержащего `internal`.
  Это механизм запрета, а не соглашение;
- тесты живут рядом: `x.go` и `x_test.go`; внешний тестовый пакет пишется как `package buildinfo_test`.

### 3.5. Организация проекта

Минимальный разумный каркас:

```
spindle/
├── go.mod
├── cmd/api/main.go              ← package main, сборка зависимостей, запуск
├── internal/…                   ← весь прикладной код
├── .gitignore
└── README.md
```

Почему так, а не иначе:

- **`cmd/<имя бинарника>`** — конвенция сообщества. Каждая директория в `cmd/` даёт свой бинарник.
  Второй бинарник (миграции, утилиты) добавляется рядом, а не пишется в `main.go` с флагом.
- **`internal/`** — гарантия на уровне компилятора, что внутренности не станут публичным API.
- **`main` — тонкий.** Он читает конфиг, собирает зависимости, запускает HTTP-сервер и воркеры,
  обрабатывает сигналы завершения. Вся логика — в пакетах. Иначе `main` превращается в
  нетестируемую простыню: тестировать её можно только через бинарник целиком.
- **Пакеты по функциональности** (`auth`, `tasks`, `projects`), а не по слоям
  (`controllers`, `services`, `repositories`, `models`). Второй вариант ты наверняка знаешь по PHP/Symfony
  и он работает, но в Go он чаще всего приводит к пакетам-«сервисам со всем сразу» и к circular imports.
  Разбор сравнения — в уроках L05–L06, пока зафиксируй как рабочее правило: *имя пакета отвечает на
  вопрос «про что этот код?», а не «какой это слой?»*.
- Никаких `utils`, `helpers`, `common`, `base` — таких пакетов не бывает. Если код не относится
  к домену, он либо относится к конкретной фиче, либо его не должно существовать.

### 3.6. Команды, которыми пользуемся постоянно

| Команда | Что делает | Когда |
|---|---|---|
| `go version` | версия тулчейна | начало |
| `go env …` | параметры окружения сборки | разбор конфигурации, L35 |
| `go mod init` | создать модуль | начало |
| `go mod tidy` | синхронизировать зависимости с импортами | после добавления импортов |
| `go build ./...` | собрать все пакеты, проверить компиляцию | перед коммитом |
| `go run ./cmd/api` | собрать и запустить | разработка |
| `go test ./...` | тесты | постоянно |
| `go vet ./...` | базовая статическая проверка | постоянно |
| `gofmt -l .` / `gofmt -w .` | проверить / исправить форматирование | постоянно |
| `go doc <pkg>` | документация пакета | чужой API |

`go vet` — не замена линтеру: он проверяет подмножество частых ошибок (форматы printf, копирование
замкнутых переменных, недостижимый код). Полноценные линтеры подключим на L41.

Форматирование: `gofmt` — стандарт, споров не вызывает (есть только `goimports` для управления
импортами и более строгий `gofumpt` — обсудим, когда появится выбор). Правило: код, который
не проходит `gofmt -l`, не считается готовым.

`go test -race` требует cgo, а cgo требует C-компилятора. На macOS это Xcode Command Line Tools
(`xcode-select --install`). Фактическая ошибка выглядит так: `go: -race requires cgo; enable cgo by
setting CGO_ENABLED=1` или `cgo: C compiler "gcc" not found`. Это не проблема Go как языка — это
требование инструмента: race detector написан на C. Мысленно полезно держать в голове различие:
`CGO_ENABLED=0` даёт статический бинарник без системных зависимостей (это то, что нужно для
контейнера в модуле 10), но `-race` внутри такого образа работать не будет. Проверь это сейчас,
чтобы не открыть для себя на модуле 3.

## 4. Сравнение с PHP и TypeScript

| Что | PHP | TypeScript / Node | Go |
|---|---|---|---|
| Описание зависимостей | `composer.json` | `package.json` | `go.mod` |
| Где живут зависимости | `vendor/` в проекте | `node_modules` в проекте | кэш модулей `GOMODCACHE`, в проект не попадают |
| Связывание импортов | autoload (PSR-4) | резолвинг при сборке/рантайме | компиляция; путь импорта = путь от корня модуля |
| Тип файла и типа | 1 класс на файл (PSR-4) | обычно 1 класс на файл | любое число типов в файле, имя файла произвольно |
| Строгость типов | `declare(strict_types=1)`, по умолчанию coercive | `strict` в tsconfig | всегда строгая, неявных приведений нет |
| Наследование | `extends` | `extends` | нет; embedding структур + интерфейсы |
| Видимость | `public/protected/private` | `public/private/protected` | экспорт по регистру; приватность — по пакету |
| Отсутствующее значение | `null` / `unset()` | `undefined` / `null` | нулевое значение (zero value) + явный `nil` |
| Рантайм | интерпретатор + php-fpm, состояние процесса между запросами | процесс node | статический бинарник, состояние в процессе приложения |
| Проверки | линтер отдельно | `tsc` + линтер | `go build` + `go vet` + `gofmt` в стандартной поставке |
| DI | контейнер (Symfony), рефлексия, аннотации | вручную или фреймворк | вручную, в `cmd/` |

Следствие для нашей работы: в Go нет «рантайм-магии», которую можно отладить только на проде.
Компилятор, `vet` и дешёвая сборка делают большую часть ошибок видимыми до запуска.

## 5. Идиоматичный пример

`internal/buildinfo/buildinfo.go`:

```go
// Package buildinfo хранит информацию о запущенном бинарнике.
package buildinfo

import (
	"fmt"
	"runtime"
	"time"
)

// version заменяется при сборке через -ldflags "-X ...buildinfo.version=v1.2.3".
// Значение по умолчанию используется в dev-сборках.
var version = "dev"

// Info — описание процесса. Экспортируются только те поля, которые нужны наружу.
type Info struct {
	Name      string
	Version   string
	GoVersion string
	StartedAt time.Time
}

// New собирает Info. Ошибок здесь быть не может, поэтому New возвращает только значение.
func New() Info {
	return Info{
		Name:      "spindle-api",
		Version:   version,
		GoVersion: runtime.Version(),
		StartedAt: time.Now().UTC(),
	}
}

// String реализует fmt.Stringer. Метод на значении: Info маленький, копировать дёшево.
func (i Info) String() string {
	return fmt.Sprintf("%s %s (go %s, started %s)",
		i.Name, i.Version, i.GoVersion, i.StartedAt.Format(time.RFC3339))
}
```

`cmd/api/main.go`:

```go
package main

import (
	"fmt"
	"os"

	"github.com/твой-логин/spindle/internal/buildinfo"
)

func main() {
	if err := run(); err != nil {
		fmt.Fprintln(os.Stderr, "fatal:", err)
		os.Exit(1)
	}
}

func run() error {
	fmt.Println(buildinfo.New().String())
	return nil
}
```

`internal/buildinfo/buildinfo_test.go`:

```go
package buildinfo_test

import (
	"strings"
	"testing"
	"time"

	"github.com/твой-логин/spindle/internal/buildinfo"
)

func TestNew(t *testing.T) {
	info := buildinfo.New()

	if info.GoVersion == "" {
		t.Error("GoVersion is empty")
	}
	if info.StartedAt.IsZero() {
		t.Error("StartedAt is zero — New must always fill the time")
	}
	if !strings.HasPrefix(info.GoVersion, "go1.") {
		t.Errorf("unexpected GoVersion: %q", info.GoVersion)
	}
}

func TestInfoString(t *testing.T) {
	ts := time.Date(2026, 9, 28, 12, 0, 0, 0, time.UTC)

	tests := []struct {
		name string
		info buildinfo.Info
		want []string
	}{
		{name: "dev build", info: buildinfo.New(), want: []string{"spindle-api", "go1."}},
		{
			name: "all fields set",
			info: buildinfo.Info{Name: "api", Version: "v1.2.3", GoVersion: "go1.27.1", StartedAt: ts},
			want: []string{"api v1.2.3", "go1.27.1", "2026-09-28T12:00:00Z"},
		},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got := tt.info.String()
			for _, want := range tt.want {
				if !strings.Contains(got, want) {
					t.Errorf("String() = %q, want it to contain %q", got, want)
				}
			}
		})
	}
}
```

Что здесь идиоматично и почему (разбираем на L05–L06 подробнее):

- `main` не содержит логики, только связывание и выход с кодом; `os.Exit(1)` вместо `panic(err)`
  — наружу из `main` ошибка уходит кодом возврата, паника тут не нужна (см. L09);
- пакет экспортирует ровно то, что нужно: `Info`, `New`, `String`; `version` — деталь реализации;
- `New()` без ошибок, потому что ошибок нет: конструктор не обязан возвращать `error` «на всякий случай»;
  в отличие от Java, где ради единообразия все конструкторы бросают исключение;
- метод на **значении** (`func (i Info) String()`), потому что структура маленькая и её не нужно
  защищать от изменения; правило receiver-ов разберём отдельно;
- тест написан как внешний пакет `buildinfo_test` — проверяет публичный API, как его увидит
  потребитель, и не даёт случайно протестировать внутренние детали;
- `var version = "dev"`, изменяемый только линкером, — согласованное исключение из правила
  «нет глобального изменяемого состояния» (N5): в рантайме переменная только читается.

## 6. Типичные ошибки переходчиков из PHP/TypeScript

1. **Классы-наследники.** `type Admin struct { User }` — это embedding, а не наследование:
   `Admin` не является `User`, у него нет полиморфизма. Попытка выстроить иерархию классов
   в Go — главный источник неидиоматичного кода. Иерархии заменяются композицией и интерфейсами.
2. **`utils`/`helpers`.** Мусорный пакет без доменной принадлежности. В Go пакет — это единица
   связности и импорта; «общий» код должен жить у потребителя.
3. **Всё в `main`.** Файл на 800 строк, покрытие 0%, невозможно переиспользовать.
   `main` — точка входа, не место для логики.
4. **Публиковать всё подряд.** Заглавная буква — это экспорт в API модуля. Публикуй осознанно;
   «всё подряд публичное» лишает смысла `internal/`.
5. **Путать версию языка и версию компилятора** (см. 3.2) и на этом нервничать при виде
   `go 1.26.0` в `go.mod` под тулчейном 1.27.
6. **Предполагать, что зависимости попадут в репозиторий.** `node_modules`/`vendor` в PHP привычны,
   в Go — нет: есть кэш, а `go.sum` фиксирует контрольные суммы.
7. **`package main` вне `cmd/`.** Случайно соберётся бинарник там, где его не ждут.
8. **Смешивать `build` и `run` в одну сущность.** В Go есть `go build -o bin/spindle-api ./cmd/api` —
   это артефакт, который можно деплоить, и это не то же самое, что `go run`.

## 7. Практическое задание

**Этап 1 — инструменты (macOS, Go не установлен).**

1. Проверить, есть ли Command Line Tools — они нужны не только для компиляции, но и для `-race`:
   `xcode-select -p`. Если ошибка «command not found» — `xcode-select --install`.
2. Установить Go одним из способов:
   - **официальный установщик** с `go.dev/dl` — архив `.pkg` для твоей архитектуры
     (Apple Silicon → `arm64`, Intel → `amd64`); ставится в `/usr/local/go`, PATH настраивается сам;
   - **Homebrew**: `brew install go` — проще обновлять (`brew upgrade go`), но версия может быть
     «плавающей»;
   - **закреплённая версия** через официальный shim: `go install golang.org/dl/go1.27.1@latest`,
     затем `go1.27.1 download`. Нужен, если хочешь работать с конкретным патчем.
   Выбери один способ и напиши в отчёте, какой и почему.
3. Проверить: `go version`, `go env GOVERSION`, и что `echo $PATH` содержит `$(go env GOROOT)/bin`.
4. **Проверить `-race` до того, как он понадобится (модуль 3):**
   ```bash
   cd /tmp && mkdir -p racetest && cd racetest
   go mod init racetest
   printf 'package main\nfunc main(){}\n' > main.go
   go test -race ./...     # без тестов напечатает "no test files" — это успех
   ```
   Если ошибка про cgo или C-компилятор — скорее всего, не установлены Command Line Tools
   или `CGO_ENABLED=0`. Разберись сейчас.

с module path вида `github.com/твой-логин/spindle` (или `gitlab.com/…` — на твой выбор;
главное, чтобы путь совпадал с адресом репозитория, иначе импорты будут неверными).

`.DS_Store`) и `README.md` на 3 коротких раздела: что это, как запустить, что внутри.

**Этап 6 — проверка и коммит.** Прогнать команды из раздела 11, сделать первый коммит.

## 8. Требования

### Функциональные

- **Ф1.** `go run ./cmd/api` печатает не менее трёх фактов о процессе: имя, версия, версия Go
  и время старта (как минимум имя + версия Go + время старта).
- **Ф2.** `go build -o bin/spindle-api ./cmd/api` создаёт исполняемый файл; `./bin/spindle-api` печатает то же самое.
- **Ф3.** Пакет `internal/buildinfo` экспортирует тип с информацией о процессе и функцию-конструктор.
  Время старта в структуре присутствует и **не является нулевым**.
- **Ф4.** `main` вызывает `os.Exit` с ненулевым кодом при ошибке старта, а не паникует.
- **Ф5.** Тесты покрывают: (а) заполненность структуры; (б) форматирование вывода, минимум
  двумя сценариями через `t.Run`.
- **Ф6.** Ни одного `package main` вне `cmd/`.
- **Ф7.** В `go.mod` ровно одна зависимость — сам модуль. `go list -m all` это показывает.

### Нефункциональные

- **Н1.** `gofmt -l .` не выводит ничего; `go vet ./...` завершается с кодом 0.
- **Н2.** `go test ./...` и `go test -race ./...` зелёные.
- **Н3.** В репозитории **ноль** сторонних зависимостей.
- **Н4.** Никакого глобального изменяемого состояния, кроме `version`, изменяемого линкером
  на этапе сборки.
- **Н5.** В `main` нет доменной логики и нет обращений к «внутренностям» пакета.
- **Н6.** Имена экспортируемых идентификаторов отражают намерение, а не тип
  (`New`, `Info` — да; `GetInfoStruct`, `DataManager` — нет).
- **Н7.** Всё, что попадает в git, прочитаемо: комментарии объясняют «почему», а не пересказывают код.

## 9. Ограничения

**Разрешено:** только стандартная библиотека. Флаги сборки, `go doc`, `go list`, `git`.

**Запрещено:**

- любые сторонние зависимости, включая `github.com/google/uuid` (в Go 1.27 есть `uuid` в stdlib,
  но на этом уроке она не нужна);
- веб-фреймворки, ORM, DI-контейнеры, логгеры;
- `interface{}` / `any`, если задача не требует (здесь — не требуется);
- генераторы, `go generate`, кодогенерация, `unsafe`;
- разбор флагов и чтение переменных окружения (это урок L35 — сейчас `main` не должен
  разбирать аргументы);
- `panic` для сигнализации об ошибках;
- `time.Sleep` в тестах;
- пакеты `utils`, `helpers`, `common`.

## 11. Команды

```bash
# 0. окружение
xcode-select -p                          # Command Line Tools; без них не будет -race
                                            # xcode-select --install, если не найдено
go version
go env GOVERSION GOTOOLCHAIN GOMODCACHE GOOS GOARCH
which -a go                              # не должно быть нескольких конфликтующих установок
echo "$(go env GOROOT)/bin" && go env GOROOT

# 1. репозиторий и модуль
mkdir -p spindle && cd spindle
git init
go mod init github.com/твой-логин/spindle
cat go.mod                        # обрати внимание на директиву go

# 2. запуск и сборка
go run ./cmd/api
mkdir -p bin && go build -o bin/spindle-api ./cmd/api
./bin/spindle-api
go build ./...                   # проверка компиляции всех пакетов

# 3. качество кода
gofmt -l .                       # должно быть пусто
gofmt -w .                       # исправить, если что-то нашлось
go vet ./...

# 4. тесты
go test ./... -v
go test ./... -cover
go test -race ./...

# 5. справка и обзор
go doc ./internal/buildinfo
go list -m all
go list -deps ./cmd/api | wc -l  # сколько пакетов stdlib тянет HTTP-сервис
```

## 13. Контрольные вопросы

1. Что означает директива `go 1.26.0` в `go.mod` и почему она не совпадает с `go env GOVERSION`?
   Что произойдёт, если поставить `go 1.30.0`?
2. Почему код в `internal/buildinfo` нельзя импортировать из другого модуля? Чем это отличается
   от соглашения «не импортировать utils»?
3. Что конкретно проверяет `go vet ./...` и почему этого недостаточно, чтобы назвать код качественным?
4. Почему в `main` мы вызываем `os.Exit(1)`, а не `panic(err)`? Что бы изменилось, если бы мы
   вызвали `log.Fatal`?
5. `main` вызывает `fmt.Println`. Это нормально или нарушение правила «main только связывает»?
   Где проходит граница?
6. Чем `go run ./cmd/api` отличается от `go build -o bin/spindle-api ./cmd/api` + `./bin/spindle-api` —
   с точки зрения скорости, артефактов и повторяемости сборки?
7. У тебя есть пакет с 30 функциями, которые «нужны всем». Почему в Go это почти всегда
   признак ошибки в архитектуре, а не в модульности?
8. `go test -race` требует cgo, а обычная сборка — нет. Какие практические последствия это имеет
   для CI на macOS и для Docker-образа, если собирать со `CGO_ENABLED=0`? Почему это ограничение
   окружения, а не самого языка?
